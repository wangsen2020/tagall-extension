## 一、这次改的是什么

把逐人提及循环，换成了**发送时改写**：用户点 `@` 按钮插入关键词（默认 `@everyone`），正常打字，按发送；TagAll 在发送动作触发的一瞬间拦截，用 WhatsApp 自己的成员名单重写这条消息，让每个人都被真实提及，消息正文保持用户原样输入的内容。

提及名单不再来自候选菜单匹配，而是直接读 WhatsApp 自己的 store（通过 WPPConnect/WA-JS 4.6.0），覆盖率不再依赖显示名匹配是否命中。群用 `@lid` 寻址，因此自我排除要比对 `conn` 报告的每一种自身 ID 形式（`getMyUserId` / `getMyUserLid` / `getMyUserWid`）。

旧的 `src/core/mentions.js`（候选菜单轮询、号码变体查询、失败清理）与 `src/core/tag-controller.js`（native/individual 分支状态机）被整体删除。

## 二、注入方式

wa-js 通过 `web_accessible_resources` 注入，而不是 manifest 的 `world: "MAIN"` content script。只有在模块运行时确认存在后才注入：

- `src/inject/bootstrap.js` 轮询等待：文档 `complete` → WhatsApp 外壳存在 → 模块运行时就绪（`window.require`/`window.__d`，或 `webpackChunkwhatsapp_web_client` 非空）→ 连续 2 次稳定检查通过，才请求注入 wa-js；
- wa-js 加载后等 `WPP.isReady` 才注入业务脚本 `src/inject/tagall-page.js`；
- 聊天切换靠订阅 `WPP.whatsapp.ChatStore` 的 `change:active` 事件，而不是纯定时器——后台标签页定时器会被节流到一分钟一次，事件订阅不受影响，定时器只作为兜底（5s 轮询）。

这套时序是 [4. wa-js方案评估](./4.%20wa-js方案评估_20260921_1919_wangsen.md) 第二节记录的生产注入序列的**简化版**：去掉了参考实现里的 `ownerToken` 抢占租约、`generation` 换代校验、能力探测分级；该文档当时已注明"若只用单一版本、不考虑与其他扩展共存，这套可以简化"，本次落地采用的就是简化版。

## 三、与此前方案评估的关系（需要注意的偏差）

[4. wa-js方案评估](./4.%20wa-js方案评估_20260921_1919_wangsen.md) 对比了三条路线，**推荐方案 B（只借读 store，不借写，仍走原生输入框由用户手动发送）**，明确不推荐方案 A（完整 wa-js 直发）。

本次实际落地的 `sendWithMentions()` 直接调用 `WPP.chat.sendTextMessage(chatId, text, { mentionedList })`，是**方案 A 的路线**：拦截发送动作、用 wa-js 直接把消息发出去，而不是把名单喂回原生输入框让用户自己按发送。

这与 [3. 研发交接](../3.%20研发交接_20260921_1839_wangsen.md) 和 [2. 产品定位](../2.%20产品定位_20260921_1743_wangsen.md) 里"扩展绝不自动发送消息，用户必须自行检查草稿并主动发送"这条产品承诺存在张力：用户虽然仍要按下 Enter 或点发送按钮触发流程，但真正发出去的内容是 TagAll 在拦截后重写生成的，不是用户在编辑器里看到并确认过的那条帯提及的草稿。是否接受这个偏差、以及 README/商店文案要不要跟着改，是产品决策，本文档只记录事实，不代做决定。

## 四、隐私文案未同步更新

本次提交没有改动隐私政策文件（见 [1. 隐私政策草稿](../1.%20隐私政策草稿_20260921_1713_wangsen.md)）。该文件仍描述"读取当前群参与者标签、写入消息输入框"的旧 DOM 方案，未反映：

- 群成员名单现在经由 wa-js 从 WhatsApp 内部 store 读取；
- 消息正文与提及列表在发送瞬间由扩展重写后交给 `WPP.chat.sendTextMessage` 直接发出。

此前已确认"需要更新隐私文案，说明名单仅本地内存使用、不落盘、不外传"，但该更新尚未落到文件里，建议下一次改动一并处理。

## 一、这次改的是什么

把逐人提及循环，换成了**发送时改写**：用户点 `@` 按钮插入关键词（默认 `@everyone`），正常打字，按发送；TagAll 在发送动作触发的一瞬间拦截，用 WhatsApp 自己的成员名单重写这条消息，让每个人都被真实提及，消息正文保持用户原样输入的内容。

提及名单不再来自候选菜单匹配，而是直接读 WhatsApp 自己的 store（通过 WPPConnect/WA-JS 4.6.0），覆盖率不再依赖显示名匹配是否命中。群用 `@lid` 寻址，因此自我排除要比对 `conn` 报告的每一种自身 ID 形式（`getMyUserId` / `getMyUserLid` / `getMyUserWid`）。

旧的 `src/core/mentions.js`（候选菜单轮询、号码变体查询、失败清理）与 `src/core/tag-controller.js`（native/individual 分支状态机）被整体删除。

## 二、注入方式

wa-js 通过 `web_accessible_resources` 注入，而不是 manifest 的 `world: "MAIN"` content script。只有在模块运行时确认存在后才注入：

- `src/inject/bootstrap.js` 轮询等待：文档 `complete` → WhatsApp 外壳存在 → 模块运行时就绪（`window.require`/`window.__d`，或 `webpackChunkwhatsapp_web_client` 非空）→ 连续 2 次稳定检查通过，才请求注入 wa-js；
- wa-js 加载后等 `WPP.isReady` 才注入业务脚本 `src/inject/tagall-page.js`；
- 聊天切换靠订阅 `WPP.whatsapp.ChatStore` 的 `change:active` 事件，而不是纯定时器——后台标签页定时器会被节流到一分钟一次，事件订阅不受影响，定时器只作为兜底（5s 轮询）。

这套时序是 [4. wa-js方案评估](./4.%20wa-js方案评估_20260921_1919_wangsen.md) 第二节记录的生产注入序列的**简化版**：去掉了参考实现里的 `ownerToken` 抢占租约、`generation` 换代校验、能力探测分级；该文档当时已注明"若只用单一版本、不考虑与其他扩展共存，这套可以简化"，本次落地采用的就是简化版。

## 三、与此前方案评估的关系（需要注意的偏差）

[4. wa-js方案评估](./4.%20wa-js方案评估_20260921_1919_wangsen.md) 对比了三条路线，**推荐方案 B（只借读 store，不借写，仍走原生输入框由用户手动发送）**，明确不推荐方案 A（完整 wa-js 直发）。

本次实际落地的 `sendWithMentions()` 直接调用 `WPP.chat.sendTextMessage(chatId, text, { mentionedList })`，是**方案 A 的路线**：拦截发送动作、用 wa-js 直接把消息发出去，而不是把名单喂回原生输入框让用户自己按发送。

这与 [3. 研发交接](../3.%20研发交接_20260921_1839_wangsen.md) 和 [2. 产品定位](../2.%20产品定位_20260921_1743_wangsen.md) 里"扩展绝不自动发送消息，用户必须自行检查草稿并主动发送"这条产品承诺存在张力：用户虽然仍要按下 Enter 或点发送按钮触发流程，但真正发出去的内容是 TagAll 在拦截后重写生成的，不是用户在编辑器里看到并确认过的那条帯提及的草稿。是否接受这个偏差、以及 README/商店文案要不要跟着改，是产品决策，本文档只记录事实，不代做决定。

## 七、浏览器实测验证（2026-09-22 补充）

关联提交：`7d4d198` feat: use a chat bubble mark instead of a rounded square（版本 0.2.8）

在真实 WhatsApp Web 上把完整链路跑通，测试群「一键拉群21」（5 人）。连续三轮，结果一致：

| 环节 | 实测结果 |
| --- | --- |
| 注入时序 | `bootstrap → wa-js 4.6.0 → tagall-page`，`stage: ready` |
| 模块运行时 | 实际走的是 **meta 运行时**（`window.require` / `window.__d`），`webpackChunkwhatsapp_web_client` 为 `null` |
| 群判定 | `ChatStore.on('change:active')` 生效，按钮自动挂载 |
| 点 `@` 按钮 | 插入 `@everyone `（含尾随空格） |
| 提及候选菜单 | **未弹出**，尾随空格用于关掉菜单的设计成立 |
| 真实按键发送 | `Enter` 键触发拦截命中 |
| 双发 | 只有一条消息，原生发送被成功阻断 |
| `mentionedJidList` | 4 个，正确排除自己（5 人群） |
| 草稿清理 | 发送后输入框清空 |

**关键发现：群成员全部以 `@lid` 寻址。** `getParticipants()` 返回的 118 个成员（另一个测试群）全是 `@lid`，而 `conn.getMyUserId()` 返回 `@c.us`。两种格式永不相等，原先 `id !== me` 的自我排除会**把自己也 @ 进去**。`getMyUserLid()` 返回的正是成员列表里的第一条。修复方式是取 `getMyUserId` / `getMyUserLid` / `getMyUserWid` 三种形式的并集排除。

**仍未验证的关键假设**：正文中不含 `@<号码>` token 时，`mentionedJidList` 能否真正触发收件人的提及通知。发送方视角看不到这一点，必须从**收件人视角**确认。这是「正文干净」这个核心卖点的基石，上线前必须验。若不成立，正文必须带 token，产品形态需要重新取舍。

## 八、实测过程中修掉的缺陷

这一节是排障复盘，五个缺陷全部由真实环境暴露，单元测试和语法检查都发现不了。

### 1. 扩展重载后按钮变「死按钮」

`mount()` 里 `if (document.getElementById(BUTTON_ID)) return;` 会认领上一个已失效上下文遗留的孤儿节点：按钮可见、样式正常，但事件监听器已经随旧上下文死亡，点击毫无反应，只能刷新页面恢复。

修复：`config.js` 增加每次加载随机生成的 `TagAll.contextToken`，`mount()` 比对 `dataset.tagallContext`，令牌不同就先 `remove()` 再重建。

### 2. 反馈循环把刷新饿死

`active-chat` 消息触发 `scheduleRefresh()`，而 `scheduleRefresh()` 内部又发 `query-active-chat` 请求，页面回一条 `active-chat`，再次触发……每次循环都 `clearTimeout` 重置 500ms 防抖，消息来得比 500ms 快，`refreshInlineButton()` **永远执行不到**，按钮永远挂不上。

修复：`scheduleRefresh()` 不再主动发查询（ChatStore 事件已覆盖会话切换），并加入 `REFRESH_MAX_WAIT = 1500ms` 上限。WhatsApp 的 DOM 持续变动，纯防抖本身就有饿死风险，上限保证最多 1.5 秒必定执行一次。

### 3. 隐藏标签页的定时器节流

长时间隐藏的标签页会被 Chrome 降到一分钟一次（intensive throttling）。原先用 `setInterval` 每秒轮询当前会话，导致按钮最多要等 60 秒才出现。改为订阅 `ChatStore` 的 `change:active` 事件，定时器降为 5 秒兜底。

这一条是从 `wd-translater-extension` 学来的——它用 `WPP.whatsapp.ChatStore.on('change:active', ...)` 监听会话切换，不依赖定时器。

### 4. `mount()` 内部的过时群判定

外层门禁已改用真实 chat id 判断是否群聊，但 `mount()` 内部还留着一层 `isGroupConversation()`（解析 header 文本里的成员名单）。成员较少的群 header 显示的是「点击此处查看群组信息」而非成员列表，解析失败，按钮被挡掉。修复：`mount()` 只要求存在输入框，是否群聊完全交给 `content.js`。

### 5. 按钮位置浮在输入框上方

原先 `footer.prepend()` 会让按钮浮在输入框上方。改为插进别针所在的图标行、排在别针左边。定位不写死 WhatsApp 的生成类名（`x100vrsf` 这类随时会变），而是从 `[data-icon="ic-attach-file"]` 找到别针按钮后向上走，直到某个节点的父元素装着多个控件，再插到它前面；找不到则回退到 `footer.prepend`。

## 九、版本号与构建标记

实测中反复出现「改了代码但不确定浏览器里跑的是哪一版」的问题，一度误判成加载了错误的目录。定下规则：

- **每次改动都递增 `manifest.json` 的 `version`**，让 `chrome://extensions` 上肉眼可辨；
- `tagall-page.js` 的 `BUILD` 常量与版本号字符串保持一致，暴露在 `window.__TAGALL_PAGE__.build`，一次 evaluate 即可判定；
- 不要用日期串做构建标记——容易忘记跟着改，反而制造新的误判（0.2.4 那次就是因为标记没跟着 sync→local 的改动更新而判断失误）。

本轮从 0.2.0 递增到 0.2.8。

## 十、商店图标

`store-assets/` 下生成 16/32/48/128 四个尺寸与 `logo.svg` 源文件，`scripts/generate-store-assets.mjs` 负责渲染（用临时目录里的 `@resvg/resvg-js`，不污染仓库依赖）。

图标为**通用聊天气泡 + 白色 `@`**，主色 `#0b8f74`。刻意不使用 WhatsApp 的听筒标志、官方绿 `#25D366` 或任何 Meta/WhatsApp 商标元素——在自有商店图标里使用他人注册商标会被 Chrome Web Store 以「暗示与知名品牌存在官方关联」直接拒审。气泡形状本身不构成商标，既能一眼看出是聊天类工具，又不会被判定为冒充。
